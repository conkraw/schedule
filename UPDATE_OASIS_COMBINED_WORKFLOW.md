## Normal workflow

1. Open **OASIS Evaluations**.
2. Choose a saved reporting period and click **Load selected dates**, or enter the two Submit Date boundaries and the report label and click **Apply reporting period**.
3. Upload the original or updated OASIS evaluation CSV.
4. The app automatically archives the original file, encrypted, and verifies recovery byte for byte.
5. It reads **all archived OASIS source exports**, checks evaluation/question identities, and removes identical repeated response rows.
6. Any missing or duplicate educator usernames are flagged on screen. Select the educator, enter the intended username, and click **Save username and continue**. The correction is encrypted in GitHub using the existing username catalog. Once the issues for the selected period are resolved, the workflow continues automatically.
7. The app creates the educator-summary CSV, encrypts it, saves it to GitHub, retrieves it, decrypts it, and checks its contents before displaying success.

There is no separate **Create CSV** button and no required download. If you upload before choosing dates, the original is still archived; the output waits for a valid, applied reporting period.

The usual result is:

> Output CSV created (or updated), encrypted, and verified in GitHub — [educator count] educators; [evaluation count] evaluations.

Only the **summary CSV** is generated as the report. No Word report, report ZIP, question-key CSV, detail CSV, or diagnostic CSV is generated by this new workflow. The code-update ZIP is an installation package, not an application report.

## Submit Date filtering

- The date filter is always **Submit Date**, never rotation Start Date or End Date.
- Both endpoints include the entire calendar day, including a submission at 23:59:59 on the end date.
- Dates are interpreted as recorded in the OASIS export; no time-zone conversion is applied.
- A custom period can cross July or last longer than 12 months without being split.
- The label is user-entered, for example `26-27`. The app does not infer an academic year from July.
- Two reports with overlapping boundaries will both include submissions in that overlap. Choose nonoverlapping periods when separate annual totals must not overlap.
- Forms without Submit Date are treated as unsubmitted and excluded with a visible count. Invalid nonblank dates stop processing rather than being silently dropped.

Example: **March 1, 2026 through March 1, 2027**, label **26-27**.

Date fields are in a form. Edits take effect after **Apply reporting period**; this avoids saving a report on every intermediate edit. Loading a saved preset applies it directly.

## Saved dates in GitHub

The dropdown reuses the existing encrypted catalog:

```text
opd_archive/reporting_date_presets.json.enc
```

Your previously saved teaching-date presets are immediately available; no migration or JSON upload is needed. OASIS interprets the selected boundaries as Submit Date boundaries. The **active OASIS date selection is independent** of the teaching-summary screen's active selection.

Under **Save or delete reporting-date presets in GitHub**:

- Enter a preset name and save the applied dates/label.
- Load a preset, change/apply the dates, and confirm replacement to update it.
- Select a preset, confirm deletion, and delete it from the current saved list.
- Refresh the preset list to obtain another session's changes.

This is a **shared preset list**. Updating/deleting a preset changes the list available to both OASIS and teaching-summary users. It does not delete OPDs, evaluations, saved output CSVs, or currently applied dates.

## Updated uploads are cumulative

Earlier evaluations are not discarded merely because they are absent from the next uploaded CSV. All existing archived originals are included in the union.

The deduplication key is:

```text
Course ID + Evaluation + Form Record + Question ID
```

The number of evaluations uses distinct submitted `Course ID / Evaluation / Form Record` keys, not question rows. A form with 19 response rows still counts once.

Examples:

- A previous export contains 10 evaluations; a new export contains those same 10 plus four new evaluations: **14**, not 24.
- A new export contains only four new evaluations: the previous 10 remain available, again yielding **14** for a period containing them all.
- An educator absent from the newest export remains in the summary if their earlier evaluations fall within the selected period/course/forms.

Averages and combined comments are recalculated from the deduplicated responses. The app does **not** append old educator-summary rows or average already-averaged scores.

### Conflicting revisions are not silently chosen

Updated exports that add new rows are merged automatically. If two archived copies give different answers or incompatible metadata for the **same** evaluation/question, the existing conflict safeguard stops the output and identifies the source/form/question on screen. It does not silently pick the newest/oldest answer, average conflicting versions, or drop either version. Merely adding a third copy does not remove a conflicting earlier archived source. Review the identified originals and reconcile the authoritative source data before generating the report.

The source archive remains intact even when reporting is blocked. The optional original-file recovery area lets you retrieve a saved source for inspection.

## Output CSV and where it is stored

The report is stored in a separate subfolder of the same configured archive:

```text
opd_archive/
    OPD_YYYY-MM-DD.xlsx.enc
    reporting_date_presets.json.enc
    oasis_educator_usernames.json.enc
    oasis_evaluations/
        OASIS_<course-dates>_<export-id>.csv.enc
    oasis_reports/
        OASIS_Summary_2026-03-01_to_2027-03-01_<scope-id>.csv.enc
```

The actual configured archive folder is used even when it is not named `opd_archive`.

**Same dates + same selected courses/forms = one current output file**, updated when the cumulative results change. Identical results do not create another unnecessary commit. A different period or different course/form selection gets its own output. Changing only the report label updates the same period's output.

Only the **active period** is rebuilt automatically. Other saved periods remain snapshots until selected/applied again. Selecting a date preset does not schedule future/background report generation.

### Columns

All existing educator-summary columns are preserved, with `record_id` first: educator name/email, evaluation count, question-specific means and scored-response counts, combined strengths and improvement comments, and identifier-status fields.

Four fields are appended:

```text
academic_year, report_start_date, report_end_date, date_basis
```

`academic_year` contains your report label; `date_basis` is `Submit Date`.

The existing calculation rules remain: averages use Multiple Choice Value, blanks/N/A are not zero, comments remain verbatim and separate by strengths/improvement, and Question IDs align form versions. The duration-category question `q1286_mean` is not interpreted as weeks or a teaching-quality score. The app shows the question key on screen, without creating another CSV.

## Missing usernames

Existing encrypted username corrections are reused. `record_id` is the username before `@` in Evaluator Email unless you explicitly supply an override. Exported Evaluator Username is shown for reference; it is not silently substituted for a missing email.

The final report waits until every included educator has a unique valid `record_id`. An educator with no source email can proceed after you save a username; the source email remains blank and `email_missing` remains `YES`. No educator is silently dropped to allow generation.

The override persists in `oasis_educator_usernames.json.enc`; no original source CSV is changed. A confirmation also permits removing an override to return to source-email identification.

## Optional review and recovery

After successful saving, expand **Optional: review or download this output CSV** to inspect the table or download the verified CSV. No download is required to complete the workflow.

**Optional: retrieve a previously saved output CSV** lists stored reports, lets you decrypt one, and offers its CSV for review. These are explicitly labeled saved snapshots, not necessarily refreshed results.

**Optional: retrieve an original archived source CSV** retains the original archive's recovery function. It returns the original bytes; it does not generate another report or alter the archive.

## Failures and concurrent changes

Original-save and output-save failures are separate and visible. An original may be stored successfully while its output is blocked by a username or data problem. A failed attempt is not repeatedly retried on unrelated widget interactions; use the explicit retry/refresh control.

Success is shown only after the saved output decrypts to the generated CSV. Before saving, the app checks the source list and username-catalog revision. It checks them again at the output's actual save commit, so a concurrent source change is not labeled a confirmed current report. A verification error can occur after a file was written; retry or refresh to verify it rather than assuming success.

Older saved outputs are not automatically deleted when a new attempt fails or an empty period is chosen. They remain previous snapshots and are not displayed as newly generated current results.

## Access, privacy, and limits

- Only ciphertext is written to GitHub by these archive/report functions. Keep your encryption key and token in Streamlit Secrets and retain a secure backup of the key.
- No app password has been added. Anyone who can access the running app can use its archive/report features unless access is restricted elsewhere.
- Optional downloads are unencrypted. Structured student identifiers are omitted from the summary, but verbatim comments can identify a student, patient, colleague, or educator. Original source downloads preserve all original fields.
- GitHub can retain prior encrypted file revisions in commit history. This workflow maintains one **current** output per date/filter scope; it does not claim permanent erasure of prior revisions.
- Existing limits remain: up to 100 cumulative source snapshots totaling 64 MiB; original CSVs up to 10 MiB each; summary CSVs up to 10 MiB. Exceeding a limit stops the workflow rather than silently omitting sources. A growing archive may eventually require a separate compaction/pagination update.
